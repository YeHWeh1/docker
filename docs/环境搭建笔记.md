## 二、搭建流程

```powershell
# 1. 准备 WSL2 与内核
dism.exe /online /enable-feature /featurename:Microsoft-Windows-Subsystem-Linux /all /norestart
dism.exe /online /enable-feature /featurename:VirtualMachinePlatform /all /norestart
# 重启后安装内核
curl.exe -L -o "$env:TEMP\wsl_update_x64.msi" https://wslstorestorage.blob.core.windows.net/wslblob/wsl_update_x64.msi
Start-Process msiexec.exe -ArgumentList "/i `"$env:TEMP\wsl_update_x64.msi`" /qn" -Verb RunAs -Wait
wsl --set-default-version 2

# 2. 安装 Docker Desktop，选择 WSL 2 backend
# 3. 启动服务
cd 'E:\dsh project'
docker compose up -d
docker ps

# 4. 验证（必须能列出 ydsh_ods 才算成功）
docker exec hive-server beeline -u "jdbc:hive2://localhost:10000" -e "show databases;"
```

## 三、问题与解决（按发生顺序）

### 问题 1：WSL 功能未启用，`wsl --install` 报「错误的网关 (502)」

**现象**

```
PS C:\Users\wei> wsl --install
错误的网关(502)。
```

**排查**

- `sc query LxssManager` / `sc query vmcompute` 均返回 `1060: 服务不存在`
  → 说明「适用于 Linux 的 Windows 子系统」和「虚拟机平台」两个功能都没启用
- 系统自带 `wsl.exe` 为 10.0.22621 旧版，不支持 `--version` / `--status`
- hosts 文件中有大量 `127.0.0.1 github.com`、`127.0.0.1 hub.docker.com` 条目
  （某拦截类软件写入），导致下载链路直接指向本机

**解决**

1. 清理 hosts 中指向 `127.0.0.1` 的非 localhost 条目（保留 `hadoop100~108` 等内网映射）
2. 用 DISM 启用两个功能（命令见上），重启
3. 内核单独下载安装（16 MB，比 `wsl --update` 的整包快得多）

**验证**

```
Test-Path C:\Windows\System32\lxss\tools\kernel   → True
KernelVersion 注册表值                            → 5.10.16
```

### 问题 2：Docker 数据默认落在 C 盘

**现象**：C 盘剩余空间从 21.4 GB 快速下降，镜像未拉取已占用 1.6 GB。

**原因**：Docker Desktop 的 WSL 磁盘（`docker_data.vhdx`）默认位于
`C:\Users\<用户>\AppData\Local\Docker\wsl\`，且 WSL 虚拟磁盘只增不减。

**解决**

Docker Desktop → Settings → Resources → Advanced → **Disk image location** → 选 `D:\Docker` → Apply & restart。

**验证**

- `D:\Docker\DockerDesktopWSL\disk\docker_data.vhdx` 存在
- `settings-store.json` 中出现 `"CustomWslDistroDir": "D:\\docker\\DockerDesktopWSL"`
- C 盘释放、D 盘减少的体积与 vhdx 大小一致

### 问题 3：镜像拉取卡死（Docker Hub 被污染 + 假镜像站）

**现象**

```
failed to resolve reference "docker.io/apache/hive:4.0.0":
dial tcp 108.160.166.61:443: connectex: A connection attempt failed...
```

换多个镜像加速站后仍然卡在 `Pulling from library/mysql`，磁盘零增长。

**排查过程**

| 镜像站 | 实测结果 |
|---|---|
| `docker.m.daocloud.io` | 直连可用，但只代理 manifest |
| `docker.1ms.run` | 同上 |
| `docker.1panel.live` | 同上 |
| `docker.nju.edu.cn` | 403 |
| `hub.rat.dev` | 可用且能拉取完整层 |

关键发现：多数镜像站对 **blob（镜像层）请求返回 307 重定向**到境外对象存储，
而该地址被阻断——所以「清单能取、层拉不动」，表现为无限等待。

**最终方案**

1. 移除 `registry-mirrors`，让 Docker 直连 `registry-1.docker.io`
2. 给 Docker Desktop 配置代理（Clash 本地端口 7897）：
   Settings → Resources → Proxies → Manual → `http://127.0.0.1:7897`
3. 速度由 0.53 MB/s 提升到约 20 MB/s，2.7 GB 镜像约 2 分钟拉完

**验证**

```
docker info --format "{{.HTTPProxy}}"   → http.docker.internal:3128
docker pull hello-world                 → 成功
```

### 问题 4：MySQL 端口冲突（本机已装 MySQL80）

**现象**：若按手册原样映射 `3306:3306`，启动时报
`Bind for 0.0.0.0:3306 failed: port is already allocated`。

**原因**：本机安装了 MySQL 8 服务（`MySQL80`），常驻占用 3306。

**解决**：不停止本机服务，仅把宿主机端口改为 `3307`：

```yaml
ports:
  - "3307:3306"
```

容器之间仍通过 `meta-mysql:3306` 访问，不受影响。

### 问题 5：Hive Metastore 启动即退出（缺少 MySQL 驱动）

**现象**

```
Error: Schema initialization failed!
Failed to load driver
Underlying cause: java.lang.ClassNotFoundException : com.mysql.cj.jdbc.Driver
```

**原因**：`apache/hive:4.0.0` 官方镜像**不包含 MySQL JDBC 驱动**，
而 Metastore 使用 MySQL 作为元数据库。

**解决**

1. 下载驱动（Maven 中央仓库）

```powershell
curl.exe -L --proxy http://127.0.0.1:7897 -o "E:\dsh project\lib\mysql-connector-j-8.4.0.jar" `
  https://repo1.maven.org/maven2/com/mysql/mysql-connector-j/8.4.0/mysql-connector-j-8.4.0.jar
```

2. 挂载进两个 Hive 容器

```yaml
volumes:
  - ./lib/mysql-connector-j-8.4.0.jar:/opt/hive/lib/mysql-connector-j-8.4.0.jar:ro
```

**验证**：Metastore 日志出现 `Initialized schema successfully..` 与 `Starting Hive Metastore Server`。

### 问题 6：Metastore 只监听 IPv6，HiveServer2 连接卡死

**现象**：三个容器都是 `Up`，但 `beeline` 报 `Connection refused`；
10000 端口未监听，容器日志停在 `Starting HiveServer2` 之后没有下文。

**排查**

1. 对 Java 进程发送 `kill -3` 导出线程栈，主线程停在：

```
"main" ... TIMED_WAITING (sleeping)
    at org.apache.hive.service.server.HiveServer2.startHiveServer2(HiveServer2.java:1140)
```

说明 HiveServer2 在**重试连接 Metastore**。

2. 查看 `/proc/net/tcp` 与 `/proc/net/tcp6`，发现 Metastore 只绑在
   `:::237B`（IPv6 通配，9083），IPv4 表中没有对应项。
3. 容器间通信走 IPv4（`hive-metastore` 解析为 172.18.0.3），因此连接失败。

**解决**：给两个 Hive 的 JVM 强制 IPv4 协议栈

```yaml
SERVICE_OPTS: >-
  -Djava.net.preferIPv4Stack=true
```

**验证**

```
/proc/net/tcp 中出现 00000000:237B（0.0.0.0:9083）  → 监听正常
docker exec hive-server beeline -u "jdbc:hive2://localhost:10000" -e "show databases;"
→ default、ydsh_ods
```

### 问题 7：容器重建后数据丢失

**现象**：重建容器后执行查询报错

```
java.io.IOException: Input path does not exist:
  file:/opt/hive/data/warehouse/ydsh_ods.db/ods_store
```

**原因**：Hive 的数据文件存放在容器的 `/opt/hive/data` 下，该目录**没有挂载卷**，
属于容器可写层；`docker compose up --force-recreate` 会连同数据一起清除。
元数据（表结构）在 MySQL 里仍在，所以表「存在但没数据」。

**解决**：增加命名卷，两个 Hive 容器都挂载

```yaml
services:
  hive-metastore:
    volumes:
      - hive-data:/opt/hive/data
  hive-server:
    volumes:
      - hive-data:/opt/hive/data

volumes:
  mysql-data:
  hive-data:
```

随后重新执行 `create_ods.sql` 与清洗脚本即可恢复（脚本可重复执行）。

**教训**：`docker compose down` 不删卷、数据安全；`down -v` 会删卷。
**判断标准**：`docker volume ls` 中应存在 `dshproject_hive-data` 与 `dshproject_mysql-data`。

### 问题 8：HiveServer2 反复重启（JVM 崩溃）

**现象**：容器状态在 `Up` 与 `Restarting` 之间反复，日志中出现

```
# A fatal error has been detected by the Java Runtime Environment:
#  SIGSEGV (0xb) at pc=0x...
# Problematic frame:
# V  [libjvm.so+0x5b8392]  G1ParScanThreadState::copy_to_survivor_space(...)
```

JVM 运行约 60 秒即在 GC 阶段崩溃，此时堆仅使用 125 MB（总 2 GB），并非内存不足。

**排查**

- 崩溃点在 GC 的对象复制路径，Parallel 与 G1 均复现
- 容器 `OOMKilled=false`，排除内存超限
- 回想：为清理 pid 文件，曾把整个 `/tmp` 挂成 tmpfs

**原因（两个叠加）**

1. `/tmp` 整个挂为 tmpfs 后，Tez 执行时的本地临时文件被放进内存盘，加剧 JVM 异常
2. JDK 8（8.0_342）在该平台的压缩指针实现存在崩溃隐患

**解决**

```yaml
hive-server:
  environment:
    SERVICE_OPTS: >-
      -Xmx2g -XX:+UseG1GC -XX:-UseCompressedOops
      -Djava.net.preferIPv4Stack=true
  tmpfs:
    - /tmp/hive        # 只给 pid 目录挂 tmpfs，不再是整个 /tmp
```

**验证**：连续执行 6 万行聚合查询，`docker inspect --format "{{.RestartCount}}"` 保持 0。

### 问题 9：容器重启后 HiveServer2 提示「已在运行」而退出

**现象**

```
HiveServer2 running as process 7.  Stop it first.
```

随后容器退出。原因是 `hiveserver2.pid` 残留在镜像内（默认写入 `$HIVE_CONF_DIR`），
重启后该 PID 恰好被其他进程占用，脚本误判为「已在运行」。

**解决**

```yaml
environment:
  HIVESERVER2_PID_DIR: /tmp/hive
tmpfs:
  - /tmp/hive
```

pid 文件写入 tmpfs，容器每次启动自动清空。

## 六、复盘：问题的三类根因

| 类别 | 涉及问题 | 说明 |
|---|---|---|
| 本机环境 | 1、2、4 | WSL 功能缺失、C 盘空间、MySQL 端口占用 |
| 网络 | 3 | Docker Hub 被污染，镜像站只代理清单不代理层 |
| 镜像缺陷 | 5、6、8、9 | 官方 Hive 镜像缺 JDBC 驱动、默认绑 IPv6、JDK8 GC 崩溃、pid 文件未清理 |
| 使用方式 | 7 | 数据目录未持久化，重建即丢 |

其中**问题 5、6 属于官方镜像的通用缺陷**，任何使用 `apache/hive:4.0.0`
并以 MySQL 作元数据库的项目都会遇到，属于可复用的经验。

## 七、经验总结

1. **容器 `Up` ≠ 服务可用**：启动后必须用业务命令（beeline）验证，不能只看状态。
2. **数据必须落卷**：凡是要保留的数据，目录一定要挂命名卷，否则重建即丢。
3. **镜像默认配置不可全信**：官方镜像的默认行为（驱动、监听地址、堆参数）需按实际环境覆盖。
4. **排障顺序**：看现象 → 看日志 → 抓线程栈（`kill -3`）→ 看 `/proc/net` → 再改配置。
5. **脚本可重复执行**：所有建表与清洗脚本使用 `create table if not exists` / `drop table if exists` + CTAS，
   环境重建后能一键恢复。
